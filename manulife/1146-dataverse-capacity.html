#1146: Dataverse database and file capacity usage, Cdn Seg Robotics Prod

Issue: Sahar-Abdoli/PowerPlatformAgent#3 · For: Sahar Abdoli Kasmaei (solution architect)

The robotics production environment keeps every desktop flow run it has ever recorded. Each run is a flowsession row. Under the default logging setup (Logs V1), the run's action log lives in a file column on that row, and that is where the 5.3 TB of file capacity sits. The job has two parts. First, agree how long run history must be kept (expected to be 1–4 weeks). Second, delete everything older on a schedule, safely. Unless logging is changed as well, the table will simply grow back.

Your role here. You own the design and the decision record: the retention rule, the delete criteria, the job design, the run order and the risk sign-off. You don't need to be the person who clicks Submit in production. An environment admin with the Bulk Delete privilege can do that once you have approved the criteria. Your deliverable is a cleanup approach that is safe, repeatable and documented, plus evidence that capacity is trending down.

1. What you should do

The steps are in order. Each one ends with a concrete output, so you can tick progress off in stand-up.

Safety baseline (read first). A bulk delete cannot be undone. If it fails partway, the rows it already deleted stay deleted; nothing rolls back. The only recovery path is Keep deleted Dataverse records, the environment recycle bin, which lasts 1–90 days and keeps counting against storage. The next fallback is an environment backup restore, which is all-or-nothing and not realistic in production. Treat every job as permanent.

Step 1: Assess (read-only), days 1–3

  • In the Power Platform admin center (PPAC), open the capacity pages: Licensing → Capacity → Dataverse → Cdn Seg Robotics Prod (or the older Resources → Capacity view). Screenshot Consumption per table for Database and File, then open each table's trend. Microsoft shows up to the last 3 months of daily trend. This is your baseline.
  • Check which tables make up the 5.3 TB of file. Flow session has three file columns: AdditionalContext (the V1 action logs), Inputs and Outputs. File data can also appear under workflowbinary or flowsessionbinary, which hold run inputs and outputs and exception screenshots. Write down which table names PPAC actually shows.
  • Read the environment's Settings → Product → Features → Desktop flow run action logs configuration and record three values: Activation status of run action logs, Action logs version (V1, V2 or Both) and, if V2 is used, FlowLogs entity time to live in minutes. Record the Action logs verbosity too.
  • On the same page, check Deleted records → Keep deleted Dataverse records and how many days it keeps. If it is on, deleted flow sessions keep using storage until that window ends, unless you tick Permanent deletion.
  • Profile the rows: count by month of completedon × statuscode. Also count rows where completedon is null (sessions that are still running, stuck or orphaned). Use the per-month approach below, because aggregate FetchXML may hit Dataverse's aggregate row limit on a table this size.
  • Find the run volume per desktop flow (regardingobjectid) and per machine group for the last 30 days. Two or three high-frequency bots usually produce most of the growth. Those are the people to talk to first.
  • Look at Settings → Data management → Bulk deletion → Recurring Bulk Deletion System Jobs. A flowsession job may already exist and be failing. Note any failures in its Run details tab.
  • Check for plug-ins or cloud flows registered on Delete of flowsession. Bulk delete triggers them once for every row deleted.
Draft FetchXML for profiling (validate first)

Draft · validate Run one month at a time. Change the two dates for each month. A plain count per window stays small enough to return.

<fetch aggregate="true">
  <entity name="flowsession">
    <attribute name="flowsessionid" alias="runs" aggregate="count" />
    <attribute name="statuscode" alias="status" groupby="true" />
    <filter type="and">
      <condition attribute="completedon" operator="on-or-after"  value="2026-01-01" />
      <condition attribute="completedon" operator="before"       value="2026-02-01" />
    </filter>
  </entity>
</fetch>

If a window still goes over the aggregate limit, split it by week, or use the Web API RetrieveTotalRecordCount function for a quick approximate total. Save every result into one table. That table becomes the "before" evidence for Step 6.

Output: a baseline sheet with per-table DB and file GB, row counts by month and status, current log settings, recycle-bin setting, the top bots by volume, and any existing bulk delete jobs.

Step 2: Agree the retention rule, week 1

  • Put a one-page proposal to the RPA owners and to compliance. Flow session history (status, timing, errors and action logs) is kept for N days after completion. N is between 7 and 28, for example 28 days for failed runs and 14 days for successful runs.
  • Confirm that no audit or regulatory process uses flow session logs as its system of record. If one does, the evidence needs to move somewhere else (a business log table, Logs V2 with Synapse Link, or an export) before any deletion starts.
  • Decide which statuses are safe to delete. Only terminal states should be in scope. Rows that are Running, Waiting, Paused or Suspended must never be in scope.
  • Decide the logging change that stops regrowth. Options: (a) set Activation status to On run failure, (b) move to Logs V2 with a TTL that matches the retention rule (this uses log capacity instead of file capacity), (c) lower the verbosity. Record who approved the choice.
Output: a signed-off retention decision (N days per status) and a logging-setting decision, both recorded in the issue.

Step 3: Build and test in a non-production environment, week 2

  • Use a dev or test robotics environment that has real desktop flow runs. If you need volume, ask the admins whether a copy of production can go to a sandbox. Weigh that against data-handling rules first.
  • Build the bulk delete query (draft below) in the Bulk Deletion wizard. Use Preview records and compare the count with your profiling numbers.
  • Run it once and check four things. Child rows are removed (file attachments, workflow and flow session binaries). Runs in progress are untouched. The desktop flow run history UI still shows the retained runs. principalobjectaccess row count changes.
  • Measure throughput (rows per hour) from the BulkDeleteOperation record's success count and its start and end times. You need this figure to size the production backlog.
Draft bulk delete criteria (FetchXML)

Draft · validate in non-prod Status values come from the published flowsession schema: 4 Succeeded, 5 Skipped, 7 Cancelled, 8 Failed, 9 Faulted, 10 TimedOut, 11 Aborted, 12 Ignored, 14 Terminated. The query leaves out 1 Paused, 2 Running, 3 Waiting and 6 Suspended.

<fetch>
  <entity name="flowsession">
    <attribute name="flowsessionid" />
    <filter type="and">
      <condition attribute="completedon" operator="not-null" />
      <condition attribute="completedon" operator="olderthan-x-days" value="28" />
      <condition attribute="statuscode" operator="in">
        <value>4</value><value>5</value><value>7</value><value>8</value>
        <value>9</value><value>10</value><value>11</value><value>12</value><value>14</value>
      </condition>
    </filter>
  </entity>
</fetch>

In the wizard this is Completed On · Older Than X Days · 28 plus Status Reason · Equals · [list]. Microsoft's own example uses Completed On · Older Than X Months · 6. Pilot variants: add <condition attribute="regardingobjectid" operator="eq" value="{desktop-flow-guid}" /> to target a single bot, or completedon before 2025-01-01 to clear only the oldest slice.

Same job through the Web API (BulkDelete action)

Draft · validate Use this when you want the job definition in source control or created by a script. RecurrencePattern takes a recurrence rule such as FREQ=DAILY;INTERVAL=1. An empty string means the job runs once. Options.CanRecoverDeletedRecords:false skips the recycle bin, so storage is released.

POST [org]/api/data/v9.2/BulkDelete
{
  "JobName": "FlowSession retention - terminal runs older than 28 days",
  "QuerySet": [{
    "@odata.type": "Microsoft.Dynamics.CRM.QueryExpression",
    "EntityName": "flowsession",
    "ColumnSet": { "AllColumns": false, "Columns": ["flowsessionid"] },
    "Criteria": {
      "FilterOperator": "And",
      "Conditions": [
        { "AttributeName": "completedon", "Operator": "OlderThanXDays",
          "Values": [{ "Value": "28", "Type": "System.Int32" }] },
        { "AttributeName": "statuscode", "Operator": "In",
          "Values": [ {"Value":"4","Type":"System.Int32"}, {"Value":"5","Type":"System.Int32"},
                      {"Value":"7","Type":"System.Int32"}, {"Value":"8","Type":"System.Int32"},
                      {"Value":"9","Type":"System.Int32"}, {"Value":"10","Type":"System.Int32"},
                      {"Value":"11","Type":"System.Int32"}, {"Value":"12","Type":"System.Int32"},
                      {"Value":"14","Type":"System.Int32"} ] }
      ]
    }
  }],
  "SendEmailNotification": false,
  "ToRecipients": [], "CCRecipients": [],
  "RecurrencePattern": "FREQ=DAILY;INTERVAL=1",
  "StartDateTime": "2026-10-20T07:00:00Z",
  "Options": { "CanRecoverDeletedRecords": false }
}
Output: a validated query, a measured rows-per-hour figure, and a list of confirmed side effects (which child tables were cleared, whether POA moved).

Step 4: Pilot in production with small, oldest-first deletes, weeks 3–4

  • Raise a change request: production data deletion, irreversible, with a named approver. Book an off-hours window when bots run least. Get the robotics team's run calendar to find it.
  • Decide on Permanent deletion. If the recycle bin is on and you don't tick it, the deleted rows go into the deleted-records store and storage doesn't drop until that retention period ends.
  • Pilot 1 is a one-off job on the oldest slice only, for example rows completed before a date at least 12 months back. Watch the job, the environment's performance and the bot runs that happen during it.
  • Work down the backlog in slices: >12 months, >6 months, >3 months, >N days. Each slice is its own one-off job, sized to fit an off-hours window using the Step 3 throughput figure. Don't start one giant job against hundreds of GB.
  • After each slice, wait 24–72 hours and re-read PPAC. Microsoft says storage figures can take up to 72 hours to update.
Output: the backlog cleared down to the retention line, with deleted counts, failure counts and storage figures logged for each job.

Step 5: Schedule the recurring job and fix regrowth, week 5

  • Create the recurring job using the agreed N. Run it daily off-hours: Run this job after every 1 day, or FREQ=DAILY;INTERVAL=1. A daily job deletes one day of runs at a time, which keeps each run small.
  • Run it under a service or admin identity that won't be disabled when someone leaves. Record the job owner in the runbook.
  • Apply the agreed logging change (On run failure, or V2 with TTL, or lower verbosity). Under V2 the TTL applies only to logs created after the change, and bulk delete isn't supported on the Flow Log table. Set the TTL correctly from day one.
  • Turn on email notification to a shared mailbox, or add the job to whatever monitoring the team already uses.
Output: a recurring job is live with a named owner, and the logging setting is changed and documented.

Step 6: Monitor and prove the trend, weeks 5–9

  • Every week, record DB GB, file GB and flowsessionbase and POA GB from PPAC, plus the flowsession row count. Compare against the Step 1 baseline.
  • Check the recurring job's Run details for failures. Failed rows land in BulkDeleteFailure.
  • If DB or file usage hasn't moved within about 2 weeks of a large slice being deleted, open a Microsoft support case (see the Ask section).
  • If POA hasn't fallen in line with flowsession, investigate why (sharing or cascade) before you consider any further action.
Output: a trend chart or table showing the reduction, as evidence for the acceptance criterion "capacity trends improve".

Step 7: Document and hand over

  • Runbook contents: the retention rule and who approved it, the exact query, the schedule, the job owner, the logging settings, how to pause or cancel the job (Bulk deletion → open job → Actions), the escalation path and the known risks.
  • Add a note for other robotics environments, which probably have the same pattern. Suggest the same standard there.
  • Close the issue with the before and after numbers.
Output: a runbook page, the issue closed with evidence, and a reusable standard for other RPA environments.

2. What you should ask

Questions are grouped by who to ask. Ask the five marked Must-ask first, because the rest of the plan waits on them.

RPA / robotics solution owners (Cdn Seg)

Must-askHow far back do you actually look at desktop flow run history and action logs, and why?
This sets the retention N from real use rather than from the 1–4 week guess. It unblocks Step 2.
Must-askDoes any bot or report read flow session records or action logs as part of its process (reconciliation, SLA reports, re-processing)?
If something depends on old sessions, deleting them breaks it. You need to find these dependencies before you choose the delete criteria.
Can we switch action logs to "On run failure", or to Logs V2 with a TTL, and lower the verbosity on high-volume bots?
This stops the 5.3 TB from growing back. Without it, the bulk delete job only treats the symptom.
When are the quietest hours for unattended runs?
This sets the off-hours window for the pilot and the recurring job.
Which flows produce the most runs or log the most actions (loops over large inputs, screenshots on error)?
This points to bot-level fixes, and tells you whether a pilot on one flow is meaningful.

Business process owners and audit / compliance

Must-askIs there a records-retention or audit obligation on RPA execution evidence for these processes, and is Dataverse the system of record for it?
This decides whether a deletion is allowed at all, and whether evidence has to be exported first. Get the answer in writing.
Do the input or output payloads or action logs contain personal or customer data?
If they do, keeping them for a short time is a privacy benefit worth stating in the decision record. It also tells you not to copy production into a sandbox for testing without approval.
Is there a legal hold that covers any of these processes?
A legal hold would require an exclusion in the delete criteria.

Environment admins (Power Platform / Dataverse)

Must-askIs "Keep deleted Dataverse records" on in this environment, and can bulk deletes on flowsession use Permanent deletion?
If deleted rows go to the recycle bin, storage won't fall for up to 90 days. This affects both the approval and the timeline.
Who holds the Bulk Delete privilege in production, and which identity should own the recurring job?
This decides who runs the job and makes sure it survives people leaving.
Are there existing (failing) bulk delete jobs, or plug-ins or flows registered on flowsession Delete?
You may find conflicting jobs, and per-row plug-in execution would make deletes much slower.
What is the change process for an irreversible production data deletion, and who approves it?
This is the path for the Step 4 change request.
Are any sharing-related settings on (for example "share reassigned records with original owner"), or is there any automation that shares flow sessions or desktop flows?
This explains the 61 GB of POA and tells you whether it will shrink as flowsession shrinks.

FinOps / capacity owners

Must-askWhat target counts as "reasonable" (GB for DB and file), and by when? Is the tenant in overage or pay-as-you-go now?
This defines what "done" means. It also tells you how urgent the work is, since overage can block environment copies and restores.
Is there capacity allocated specifically to this environment, and are alerts configured?
Alerts could double as the ongoing monitor for Step 6.
If you move to Logs V2, is there enough Dataverse log capacity?
V2 moves the cost from file capacity to log capacity, so the log side needs sizing first.

Microsoft support (only if needed)

Ask if storage hasn't dropped about 72 hours to 2 weeks after a large confirmed delete, or if POA doesn't shrink: "Is space reclaimed for flowsession file columns and the POA rows tied to deleted records? Is there a backend cleanup still pending?"
Direct deletion on POA isn't supported, so only Microsoft can confirm orphaned access rows or run a backend cleanup. Bring the BulkDeleteOperation IDs and your before and after numbers.
What throughput should we expect from bulk delete for flowsession at this volume, and is there a faster supported route for a one-time backlog?
This matters if the backlog would take weeks of off-hours windows. Fast delete mode is documented as sandbox-only.

3. What you need to learn

Topics are in priority order. The badge shows how deep you need to go for this task.

ExpertBulk delete jobs: wizard, API, recurrence, permanent deletion, failure handling

This is the main tool for the task. Key facts: a job deletes only records created before it starts. It follows cascade rules and fires plug-ins on every row. It never rolls back. Permanent deletion (CanRecoverDeletedRecords:false) skips the recycle bin. Out-of-the-box recurring system jobs let you change their schedule but not their query.

Remove data with bulk deletion · Delete data in bulk (BulkDelete / Options) · View and act on bulk deletion jobs
ExpertDesktop flow run history: the flowsession table and its children

A desktop flow run is a flowsession row. Its file columns are AdditionalContext (V1 logs), Inputs and Outputs. Microsoft documents a cascade to Workflow Binary, which holds inputs, outputs and exception screenshots, so deleting the session removes those binaries. Know the statuscode values and the completedon and regardingobjectid fields well enough to write criteria from memory.

Delete desktop flow run history data · flowsession table reference · Monitor desktop flow runs
ExpertDesktop flow action logs: V1 vs V2, activation status, verbosity, TTL

V1 is the default and stores logs as a file blob in AdditionalContext, which uses file capacity and has no automatic retention. V2 stores logs in the flowlog elastic table, which uses log capacity and has a built-in TTL. Settings: Activation status (Enabled, On run failure, Disabled); verbosity (Full, Debug, Custom, Warning, Error); and FlowLogs entity time to live in minutes. Recent change to note: the TTL applies only to new logs. V2 works only for runs launched from a cloud flow. Changing versions doesn't migrate existing logs. Bulk delete isn't supported on Flow Log. Check whether V2 is GA or still preview for your tenant before you recommend it for production.

Desktop flow action logs configuration · Elastic tables
WorkingCapacity reporting and when space is reclaimed

Learn the PPAC per-table consumption view and its daily trend, which covers up to 3 months. Storage figures can take up to 72 hours to update after deletions, and capacity is evaluated about every 24 hours. File and database are pooled at tenant level, and log capacity is separate. Overage can block environment lifecycle operations such as copy and restore.

Dataverse capacity-based storage · Free up storage space
WorkingDeleted record keeping (recycle bin)

When it is on, deleted rows count against storage for 1–90 days. "Delete all records" purges them. This is the most likely reason that "we deleted it and nothing changed".

Restore deleted Dataverse table records
WorkingPrincipalObjectAccess (POA): why it grows and how it shrinks

POA stores direct shares, team shares, access-team membership and access inherited through cascade-share or reparent relationships. Deleting rows from it directly isn't supported. You shrink it by changing the security model (revoke sharing, change cascade, run the inherited-access cleanup). Expect it to shrink as flowsession rows are deleted only if the POA rows belong to flowsession records. Confirm that first.

Manage PrincipalObjectAccess storage · Table relationship cascading behavior (reparent / inherited access)
AwarenessFetchXML aggregate limits and counting at scale

Aggregate queries on very large tables can fail when they hit the aggregate row limit. Count in date windows instead. Use RetrieveTotalRecordCount for fast approximate totals.

AwarenessDataverse long-term retention

This is an archive alternative to deletion, for cases where compliance needs history kept but not in the active database. Per the logs doc, it isn't supported for V1 action logs. It is worth knowing exists if compliance asks for "keep but cheaper".
