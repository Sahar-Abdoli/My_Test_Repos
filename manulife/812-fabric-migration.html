#812 – Fabric / Power BI: Premium P SKU → Fabric F SKU migration

GitHub issue Sahar-Abdoli/PowerPlatformAgent#2 · recycled 2026-10-02 as the umbrella initiative

In plain language: Manulife runs Power BI on Premium P1/P2/P3 capacities, a product Microsoft has stopped selling and is retiring. Every one of them has to move to a Fabric F capacity bought through Azure. The preferred approach is like-for-like: one F capacity per existing P capacity, sized from real usage data rather than a straight P-to-F mapping. Cost centers provision their own F capacity through a Cloud Catalog self-service module and move their workspaces. Your team writes the guidance and switches off the old P capacities. Fabric’s other workloads (OneLake, warehouses, Spark and so on) stay locked down until the Global Data Office finishes its due diligence.

Reuse opportunities in your PPOps toolkit (/home/user/powerplatformagent)

What exists today:

  • ppops pbi ls (src/PPOps.Cli/Commands/PowerBiCommands.cs) lists workspaces with their capacity SKU, using FabricService.WorkspacesAsync (Fabric /v1/workspaces joined to /v1/capacities). Limitation: these are user-scoped endpoints, so it only sees workspaces and capacities the signed-in user can access. It can’t produce the tenant-wide picture behind 88 vs 53.
  • Doctor.CapacityTypeAsync already classifies a capacity by SKU (shared, P, F, PPU, trial). That logic can be reused for SKU-family bucketing.
  • diagnose pbi-refresh (PbiRefreshPlaybook) already detects capacity, memory and timeout refresh failures. It’s useful for post-move validation of critical semantic models.
  • The plan → apply → verify → rollback model, with its hash-chained audit log, fits workspace reassignment well.

Worthwhile extensions (in a branch; I haven’t changed the repo):

  1. Read-only inventory capacities command: calls Power BI admin GetCapacitiesAsAdmin plus Fabric admin /v1/admin/workspaces (which returns capacityId), then outputs a CSV of capacity → sku family → region → state → admins → workspace count. Diffing it against a Command & Control export gives you a repeatable 88-vs-53 reconciliation playbook for #1130. It needs Tenant.Read.All and a Fabric admin role, which means an admin-consent conversation.
  2. Plan-gated reassign executor: Fabric POST /v1/workspaces/{id}/assignToCapacity (async, 202), verified by Power BI CapacityAssignmentStatus, with rollback back to the original P capacity id. This is useful for ETS-owned workspaces and for helping stuck cost centers, without giving them admin rights.
  3. Pre-move check: flags large-format models, non-Power BI Fabric items, and a target capacity in a different region from the source.

Recent changes to know about (verify before relying on them):
  • Capacity overage reported GA at FabCon Europe (29 Sep 2026). Excess CU is billed on a separate meter, reported at about 3× the pay-as-you-go rate, up to an admin-set rolling 24-hour threshold. Reservations don’t cover it. Secondary sources disagree on whether it’s on by default for new capacities, so check the setting on the first F capacity #238 creates.
  • From 15 Oct 2026, OneLake operations run by Spark are reported to count toward OneLake CU consumption. This matters only if GDO allows Spark, but it changes Metrics app baselines.
  • Workspace-level surge protection, on-demand billing and an F0 SKU have been announced, with mixed preview/GA status. Don’t design around them yet.
These items come from the Fabric community blog and secondary write-ups. I couldn’t open the Learn pages in full from here, so confirm them with the Microsoft account team.
