#1037P — Power Pages: operationalize as a supported service

Status: Exploratory Owner: Sahar Abdoli Kasmaei (Solution Architect, ETS Power Platform) GitHub issue #1

In plain language: Manulife doesn't offer Power Pages (Microsoft's low-code website product) as a supported service today. This task designs how it would be offered: who owns it, who can ask for a site, how a site is approved and secured, how it sits behind Akamai, how its Entra app registrations get created (ideally automatically), how environments and production releases work, and who supports it afterwards. The outcome is an approved service model, governance, and a roadmap, so that Segment IT teams can build and run their own sites safely. SinoChem's specific requirements are out of scope.

Your likely role: design authority and facilitator. You own the target operating model and the technical reference architecture (edge/Akamai, identity, environments, ALM). You coordinate decisions from InfoSec, Network, Identity and Segment IT. You don't build individual sites.

What you should do

Prioritized and phased. Tick items off as you go (the checkboxes don't save). Each item names the artifact it should produce.

First 2 weeks: frame the problem and unblock the big unknowns

  • Inventory what already exists. Find any Power Pages or legacy Power Apps portal sites in the tenant: Power Platform admin center → Resources → Power Pages sites, plus the CoE Starter Kit inventory if it's deployed. Record each site's environment, owner, visibility (private/public), data model (standard/enhanced), auth providers, custom domain and whether anonymous table permissions exist. Output: current-state site inventory (spreadsheet), including "shadow" trial sites.
  • Snapshot the tenant governance settings that already apply: whether non-admins can create sites (disablePortalsCreationByNonAdminUsers), the "site visibility" and "disable anonymous access" governance controls, "enable external authentication providers", Managed Environments status, and DLP policies on the target environments. Output: "control baseline" table showing each setting, its current value and the proposed value.
  • Book the 5 must-ask conversations (see What you should ask), starting with InfoSec and the Akamai/network team. The Akamai pattern is the biggest technical unknown and drives the hosting design. Output: stakeholder map (RACI draft) and meeting notes.
  • Get at least two real candidate use cases from Segment IT leads: one internal (employees or advisors on Entra ID) and one external (customers or partners). Use them to test every design decision. Output: 1-page use-case cards (audience, data sensitivity, identity, volume, deadline).
  • Stand up a sandbox site in a non-production environment to learn the controls hands-on: site visibility, Entra ID sign-in, table permissions, WAF/IP restriction options (some need production state), and the Security agent (preview). Output: lab notes with screenshots, which seed the Phase 2 runbooks.

Phase 1 — Discovery

  • Write the current-state assessment covering existing sites, current controls, licensing/capacity position (authenticated and anonymous capacity packs, or none), and who holds which admin roles today. Output: Current-State Assessment doc.
  • Define site risk tiers. Proposed: T1 internal-only (Entra workforce, private); T2 external authenticated (customers or partners via Entra External ID or another OIDC IdP); T3 anonymous/public with Dataverse data exposed. Each tier sets the approvals, security review depth, identity options and support level. Output: risk-tier matrix, reviewed with InfoSec and Risk.
  • Run an Akamai integration proof of concept on the sandbox: Akamai property pointed at the Power Pages origin, Host-header behaviour, custom-domain binding and validation (Power Pages needs a publicly resolvable CNAME), sign-in redirect URIs, cookies, caching rules, and locking the origin to Akamai (Power Pages IP restriction against Akamai egress ranges). Also decide whether the built-in Power Pages WAF/CDN (Azure Front Door based) is switched off or layered underneath. Output: Akamai reference architecture plus PoC test results (pass/fail per check).
  • Map the app registrations each pattern needs: Entra ID workforce sign-in (OIDC, one per site/environment, with reply URL on the site host), Entra External ID (registration in the external tenant), plus optional integrations (SharePoint document management, Power BI embedding, server-side calls to APIs). Note the secret/certificate owner and rotation for each. Output: app-registration catalogue (purpose, tenant, redirect URIs, permissions, credential type, rotation owner).
  • Capture the security requirements (pen test, OWASP checks, logging to SIEM, data classification, privacy/PIA) and the compliance requirements (accessibility, regional data residency, records retention). Gap them against what Power Pages provides natively. Output: security and governance requirements register, plus a readiness-gap list.
  • List the integrations and dependencies: Dataverse environments, DLP, ServiceNow (or whatever tool handles requests and incidents), DNS, certificate management, SIEM, and identity. Output: dependency map (one diagram).

Phase 2 — Service design

  • Define the target operating model. I'd recommend starting assisted: Segment IT builds; ETS owns the platform, environments, domain/Akamai, app registrations and the production deployment gate. Allow self-service later, only for T1 sites. Keep managed (ETS-run) as an exception for T3. Output: Target Operating Model, with a RACI per lifecycle stage (request → build → review → deploy → run → retire).
  • Design the environment pattern: a dev/test/prod set per Segment (or per site for T3), Managed Environments on, enhanced data model only, and site creation restricted to admins or provisioning automation. Output: environment strategy and naming convention.
  • Design ALM: sites live in solutions (enhanced data model), deploy via Power Platform pipelines into production, with no direct maker access in prod. Table permissions and site settings travel in the solution; environment-specific values (client IDs, domains) go in environment variables or deployment settings. Output: ALM and release standard, including the production change gate.
  • Write the onboarding package for Segment IT: request form fields, prerequisites (licensing/capacity, data owner, InfoSec intake), a training path, a site build checklist (table permissions, web roles, no anonymous Dataverse data unless approved, security headers) and a go-live checklist. Output: Segment IT Onboarding Guide plus checklists.
  • Define the support model: L1/L2/L3 split, the Microsoft support path, monitoring (capacity reports, Security agent scans, Akamai/WAF logs to SIEM), secret/cert expiry alerts, and incident runbooks (site down, auth broken, WAF false positive, data exposure). Output: Support Model plus runbooks.
  • Specify the automation requirements: environment provisioning, app-registration creation and rotation, Akamai property/DNS request, IP-restriction sync, and governance scans. See "Reuse from PPOps" below. Output: automation backlog with effort/value scoring.

Phase 3 — Implementation planning

  • Build the roadmap: MVP (assisted, T1 plus one T2 pilot), then hardening (automation, SIEM), then scale (self-service T1, more segments). Output: roadmap with dates and dependencies, for approval.
  • Prioritize the automation by toil removed and risk reduced. Likely order: (1) app registration plus site-settings generation, (2) environment provisioning, (3) governance scan/report, (4) secret-expiry alerting, (5) Akamai/DNS request integration. Output: prioritized automation backlog.
  • Plan the rollout: pilot with one Segment IT team, run a retrospective, then a wider launch. Set the policy for existing sites (migrate, re-platform or decommission). Output: rollout and communications plan.
  • Define success metrics, for example: time from request to dev environment; time to production; % of sites with no anonymous Dataverse access; 0 expired auth secrets; Security-agent findings closed within SLA; number of Segment IT teams onboarded. Output: KPI sheet plus dashboard spec.
  • Take the service model, governance and roadmap to the approval forum, and get sign-off against each success criterion in the issue. Output: approval record mapped to the issue's 7 success criteria.
Reuse from PPOps (your toolkit at /home/user/powerplatformagent)

Opportunities I can see from the code that actually exists. PPOps doesn't cover any of these today; each would be an extension.

  • App-registration automation template. src/PPOps.Auth/AppRegistration.cs already generates a manifest, an admin-consent URL and an az script that resolves permission IDs from the resource service principal at run time instead of hard-coding them. A pages register-site-app variant could reuse that pattern. It would need a different app shape: a web/confidential client with the site's OIDC reply URL (not the public client PPOps uses), a certificate or secret, and the matching Power Pages site settings emitted for the solution or deployment settings.
  • Governance checks via the Doctor pattern. src/PPOps.Admin/Doctor.cs (capability report with checks and compact tables) and Dlp.cs (policy evaluation per environment) are a good base for a "Power Pages posture" scan, e.g. sites with anonymous table permissions, public non-prod sites, sites without a custom domain behind Akamai, or auth secrets near expiry.
  • Environment inventory. BapAdmin.ListEnvironmentsAsync / PowerPlatformAdmin in AdminClients.cs can feed the Phase 1 inventory.
  • Human-gated production changes. PPOps's plan → approve → apply → verify → rollback model fits the ETS production gate for site-setting or IP-restriction changes.

LimitThe Power Pages admin API (used for things like IP allow-lists and WAF rules) documents that the service-principal flow isn't currently supported. Fully unattended automation of those settings may not be possible yet, so check this before you commit to it.

What you should ask

Grouped by who to ask. Must-ask marks the five to ask first, because they unblock the most downstream decisions.

InfoSec / Security architecture
Must-ask Is an externally facing, Microsoft-hosted SaaS website (Power Pages) acceptable for external customers or partners at all? If yes, what's the minimum security review per risk tier (threat model, pen test, DAST)? This decides whether T2/T3 are in scope for MVP and sets the approval workflow.
Must all internet-facing sites sit behind Akamai, or is Microsoft's built-in WAF (Azure Front Door based) acceptable for some tiers? If Akamai is mandatory, the PoC is on the critical path. If not, T1 can launch sooner.
What logs must reach the SIEM (Akamai/WAF, sign-in, Dataverse audit), and within what latency? This feeds the monitoring design and Dataverse auditing settings.
Can anonymous visitors ever read Dataverse data? Should "disable anonymous access" be tenant-wide by default, with exceptions? This sets the default governance control and the exception process.
What are the standards for client secrets vs certificates on app registrations, and the rotation period? This drives the app-registration automation design and expiry monitoring.
Network / Akamai team
Must-ask What's the standard pattern for putting a third-party SaaS origin behind Akamai? Specifically: Host-header forwarding, origin TLS validation, SiteShield or a fixed egress IP list we can allow-list in Power Pages IP restriction, and how domain-validation CNAME/TXT records are handled when the public CNAME points to Akamai. This is the core of the "Akamai approach defined" success criterion. Microsoft documents Azure Front Door, not Akamai, so you need the network team's pattern and a PoC.
Which caching and bot-management rules apply by default? Can we exclude authenticated paths, sign-in endpoints (/signin-*), and the Power Pages Web API (/_api/)? Caching personalised content or blocking sign-in callbacks are classic breakages.
Who owns DNS and certificates for Manulife domains, and what's the lead time for a new hostname and certificate? This sets the onboarding SLA. Power Pages custom domains need a cert (PFX) unless managed differently.
Are there private-connectivity needs (sites calling on-prem APIs)? This decides whether you need gateways, Azure API Management or VNet patterns.
Entra / Identity team
Must-ask What's the approved identity provider for external users: Entra External ID (an external tenant), an existing customer IAM platform, or something else? Does Manulife already run an external tenant? This decides the T2 identity pattern and which tenant app registrations live in.
Will Identity allow ETS (or an automation service principal) to create app registrations, with a scoped role such as Application Developer plus owner assignment, or must each one go through a ticket? This decides whether "app registration automation" means full automation or a generated request package.
What are the naming, ownership and Conditional Access policies for app registrations used by websites (MFA for employees, guest access)? This feeds the governance doc and the automation template.
Power Platform CoE / ETS leadership
Must-ask Who owns the Power Pages service: ETS end to end, or ETS for the platform and Segment IT for the sites? What funding model applies to capacity (authenticated and anonymous packs, or pay-as-you-go per environment)? This is the ownership and cost model. Without it the service model can't be approved.
Which approval forum signs off the service model and roadmap, and what format does it expect? This gives you the approval path for the success criteria.
Are Managed Environments and pipelines already the standard for other Power Platform workloads? Is there a provisioning process to extend? Reusing what exists cuts the work significantly.
Can we restrict site creation tenant-wide now, before the service exists? This stops more shadow sites appearing during discovery.
Segment IT leads
Must-ask What sites do you actually want to build in the next 12 months? Who are the users (employees, advisors, customers, partners), what data do they touch, and what's the deadline? Real demand sizes the MVP and the self-service vs assisted split, and gives you pilot candidates.
What Power Platform and web skills do your teams have (Liquid, JavaScript, Dataverse security)? Can you staff L1/L2 support for your own sites? This decides how much ETS has to own, and what training goes in onboarding.
Do you have existing Power Apps portals or other sites you'd expect to move? This sets migration scope (standard → enhanced data model).
Compliance / Risk / Privacy
Which regulations apply to externally facing sites per jurisdiction (privacy notices, cookie consent, accessibility such as WCAG/AODA, records retention, data residency)? These become go-live checklist items and may limit which Dataverse regions can host sites.
Is a privacy impact assessment or a third-party/vendor risk assessment needed once for the service, or per site? This sets per-site onboarding lead time.
What risk-acceptance process applies to preview features (e.g. the Security agent) and to Microsoft-managed WAF rules you can't fully see? This decides which Microsoft controls you can rely on vs only use as extra protection.
Microsoft (account team / FastTrack / support), if available
Is running Power Pages behind a third-party CDN/WAF (Akamai) with a custom domain supported? Are there known issues with Host headers, domain validation or IP restriction seeing the client IP vs the edge IP? This gets a supportability statement on record before you commit to the architecture.
What's the roadmap for service-principal support in the Power Pages admin API? This determines whether IP/WAF configuration can be automated unattended.

What you need to learn

In priority order. Depth: Awareness know it exists and its limits · Working can configure and explain it · Expert can design it and defend it to InfoSec.

Expert1. Edge security: built-in WAF/CDN (Azure Front Door) vs Akamai, plus IP restriction

This is the hardest design question in the task. Power Pages' own WAF runs on Azure Front Door and works in Prevention mode with managed rules. Microsoft's documented "bring your own edge" pattern is Azure Front Door, not Akamai. IP restriction (public IPs only, static 403 page) is the main way to force traffic through your edge.

WAF for Power Pages · Set up Azure Front Door with Power Pages · Restrict website access by IP address · Add a custom domain name

Expert2. Authentication and app registrations

You need this to define which app registrations exist and whether they can be automated. Learn the OIDC provider settings (client ID, reply URL, secret in site settings), Entra ID for workforce, and Entra External ID for customers (the setup wizard was reworked in 2025). Note that Azure AD B2C is no longer the default choice for new customer identity; check its sales status with Identity.

OpenID Connect provider settings · Microsoft Entra External ID with Power Pages · 2025 wave 1: External ID setup wizard

Expert3. Tenant governance controls for Power Pages

These controls are the core of the governance document. Sites are private by default. Admin governance controls cover site visibility for non-production sites, disabling anonymous access to Dataverse data, and external authentication providers. Site creation by non-admins is blocked via a PowerShell tenant setting.

Site visibility · Governance control: disable anonymous access · Control site creation · Power Pages governance (CoE)

Working4. Data security model: table permissions, web roles, column permissions

Most real data exposures come from this layer: a Global-scope permission tied to the Anonymous role. Your build checklist and security review depend on it. Remember that rights add up across roles and can't be reduced by another role.

Working5. ALM: enhanced data model, solutions, pipelines, PAC CLI

This is needed for the production deployment process. Solution-based ALM and pipelines only work for enhanced-data-model sites (the default for new sites since 2023). Migrating standard → enhanced is via pac pages migrate-datamodel (preview).

Working7. Licensing and capacity

This drives the funding and chargeback model. Capacity comes as authenticated and anonymous packs or pay-as-you-go, set per environment. Internal users with Power Apps or Dynamics 365 licences may not need capacity. Monitor with the consumption reports.

Awareness8. Security agent (preview) and admin API

Candidate inputs to operations. The Security agent runs scheduled OWASP-ZAP-based scans and traffic monitoring; it's in preview, so treat it as extra, not a control InfoSec relies on. The admin API covers IP allow-list and WAF operations, but doesn't currently support service principals.

Recent changes worth knowing (as of Oct 2026)
  • Private by default: new sites are private (Entra sign-in for makers' invited users). Non-production sites can only go public if admins allow it via the site-visibility governance control (default "None").
  • Security agent (preview) in the design studio succeeds the earlier Security Checker/Meter preview. Its documented scope has grown to authentication, authorization and header reviews, with fixes that need approval. Check which one your tenant shows.
  • Entra External ID setup wizard built into Power Pages (2025 release wave 1). Older step-by-step blog posts are out of date.
  • Enhanced data model is the default. No end-of-support date for the standard model has been announced, but solution/pipeline ALM requires enhanced, so make it mandatory for the new service.
  • WAF and CDN are separate toggles, both on Azure Front Door. CDN custom-domain TXT validation must be completed within 7 days of enabling.

Risks & watch-outs

  • Akamai in front of a SaaS origin you don't control. Power Pages routes by host name and generates absolute URLs and sign-in redirects from it. If Akamai forwards the wrong Host header, sign-in loops and broken links follow. Also, custom-domain validation expects a public CNAME to the Power Pages host, which conflicts with the CNAME pointing at Akamai. Prove this in the PoC before you promise dates.
  • The edge can be bypassed. The *.powerappsportals.com host stays reachable unless you restrict it. Plan IP restriction to Akamai egress ranges, and confirm whether IP restriction evaluates the edge IP or a forwarded client IP.
  • Two WAFs/CDNs stacked (Akamai plus Power Pages WAF/CDN) cause double caching, confusing false positives, and two rule sets to tune. Choose one primary deliberately.
  • Caching personalised pages. Akamai rules must not cache authenticated content or /_api/ responses.
  • Anonymous data exposure. A Global-scope table permission on the Anonymous role is the most common real-world leak. Default "disable anonymous access" on, with exceptions approved.
  • Expiring client secrets on site identity providers take a site's sign-in down silently. Prefer certificates or managed rotation, and alert on expiry.
  • Automation ceiling. The admin API doesn't support service principals, and app-registration rights may stay with Identity. "Automation" may end up as generated request packages plus approvals, so set expectations early.
  • Shadow sites: trial sites created before governance lands. Restrict creation now and include them in the inventory.
  • Capacity cost surprises. Anonymous and authenticated capacity is per environment and can't be swapped between the two types. Pay-as-you-go costs more per user. Agree chargeback before onboarding.
  • Over-relying on preview features (Security agent, migration tool). Keep them as extras, not controls InfoSec depends on.
  • Scope creep into SinoChem or individual site builds. Both are explicitly out of scope; log them and park them.
